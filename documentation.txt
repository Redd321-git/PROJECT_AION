	requirements for decision maker diagnostic logics:
		progress check logic:
			1) must maintain a buffer that keeps track of the existing goals and the new ones that occur and the completed ones to be discarded from the buffer
			2) must intimate decision maker to reach out planner or the operator for updating the runtime config file when ever it comes across a new goal type that it hasn't seen before

	"turns out i am actually changing the architecture of AION a bit in between decision maker and planner like i previously thought but on a lower scale. what actually happened while i was thinking of the code and logic of the progress check logic of the decision maker i found out that goals are not restricted to a single type they vary like {production goal is if it can satisfy all the dues date of product supply}, {try to reduce the power consumption this month } etc etc... but previous i thought of maintaining hardcoded function for goal specific progress checks but as this goals are very uncertain so what i did in the diagnostic logics i gave a option of intimating the decision maker to reach out the planner for novel cases when it doesn't have logic to assess the current situation then operator is to actually provide the logic for the progress check if he doesn't then he can give access to the planner for the logic generation to the planner. planner capable of generating logics for these novel scenarios can add new logic to the decision maker constantly evolving and contributing to the overall adaptability of AION to new situations "
